# ADR 0006 — ID numérico autoincremental vs código de negocio

## Estado

Aceptado — 2026-06-02

## Contexto

Los catálogos (materia prima, proveedor, animal) se modelaron inicialmente con `id VARCHAR(32)` generado en aplicación (`IdGenerator`), mezclando el rol de identificador técnico con el código que el usuario ve en pantalla.

Eso generaba confusión: el usuario piensa en "MAIZ" o "P001", no en `mpx9uo1te5r1ndc62kyqh4r9`. Además, el ID técnico debe ser estable, único e irrepetible aunque el registro pase a inactivo; el código es la clave de negocio editable y reutilizable solo entre activos (ADR 0005).

## Decisión

Para **t_materia_prima**, **t_proveedor** y **t_animal**:

| Campo | Tipo | Origen | Regla |
|-------|------|--------|-------|
| `id` | `BIGINT` | BD (`GENERATED BY DEFAULT AS IDENTITY`) | PK, único global, nunca se reutiliza al soft-delete |
| `codigo_*` | `VARCHAR(50)` | Usuario (API) | Único entre filas **activas** de la misma granja (índice parcial) |

- JPA: `@GeneratedValue(strategy = GenerationType.IDENTITY)` en `Long id`.
- En `crear()` **no** se asigna `id` en el builder; lo genera Postgres al `save`.
- Las rutas REST usan el id numérico en PUT/DELETE: `/api/materias-primas/{idGranja}/{id}`.
- La UI muestra y filtra por **código** y descripción/nombre; el `id` numérico se usa solo para operaciones REST internas.

**Usuario y Granja** siguen con `VARCHAR(32)` y `IdGenerator` hasta una migración futura (rutas y JWT ya dependen de `u_demo` / `g_demo`).

## Consecuencias

- Migración `V005` convierte PK y FKs de catálogo a `BIGINT`; vacía datos dependientes (dev: re-seed).
- DTOs y frontend: `id: number` / `Long` en respuestas.
- FKs en compras, fórmulas, inventario referencian `BIGINT` al implementar esos módulos.
